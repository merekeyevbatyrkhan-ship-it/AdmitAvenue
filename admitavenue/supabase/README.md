# База AdmitAvenue: первый этап

Миграция выполнена пользователем в проекте команды: SQL Editor вернул успех, проверка — RLS true/true и четыре политики. Сайт подключён через публичную конфигурацию; добавлены Auth и сохранение анкеты. Реальный цикл входа и записи ещё нужно проверить после настройки адресов возврата.

## Что создаём

Сначала одну таблицу `public.admit_profiles`: одна анкета на одного вошедшего пользователя. Все поля текущей анкеты хранятся вместе в `draft` типа JSONB — структурированном документе PostgreSQL. Так не теряются массивы экзаменов, языков и достижений, а сохранение всей анкеты выполняется одной операцией.

| Колонка | Назначение |
| --- | --- |
| `user_id` | Идентификатор пользователя из Supabase Auth |
| `draft` | Профиль формата версии 1 из `public/profile-core.js` |
| `current_step` | Последний открытый шаг, от 0 до 6 |
| `locale` | ru, kk или en |
| `revision` | Номер версии записи для защиты от конфликтов сохранения |
| `created_at`, `updated_at` | Серверные даты |

Логины и пароли будут обрабатываться Supabase Auth; собственную таблицу паролей не создаём. Таблицы университетов, рекомендаций, маршрутов и переписки добавим отдельными миграциями при реализации этих функций.

## Как применить

1. В Supabase открой проект AdmitAvenue и раздел SQL Editor (`>_` в левой панели).
2. Создай новый запрос и вставь содержимое `migrations/202609180001_applicant_profiles.sql` целиком.
3. Нажми Run. Скрипт создаёт новую таблицу, функцию, триггер и правила; существующие данные не удаляет.
4. Успешный результат обычно сообщает, что запрос выполнен без возвращённых строк.
5. Отдельно выполни `verify.sql`: ожидаются включённый RLS и четыре политики.
6. Открой Table Editor → `admit_profiles`. Запись появляется после входа на сайте и явного сохранения анкеты.

Не запускай миграцию повторно: сообщение об уже существующем объекте требует проверки состояния, а не удаления таблицы. Внутри используется транзакция: при ошибке изменения этого запуска не фиксируются.

## Подключение сайта

Понадобятся Project URL и **publishable key** (`sb_publishable_...`) из проекта. Старый `anon` key тоже является клиентским ключом, но предпочтительнее современный publishable key. Database password, `service_role`, `sb_secret_...` и ключ AI API для клиентского подключения не нужны.

После настройки Supabase Auth клиент получает пользовательский access token. Именно он, вместе с ключом проекта, позволяет RLS определить владельца анкеты. Один publishable key сам по себе не даёт анонимному пользователю доступа к анкетам.

Реализовано: гостевой черновик → явный вход → выбор анкеты → чтение/сохранение собственной анкеты. Перенос гостевого черновика поверх существующей анкеты требует подтверждения в интерфейсе. Обновления проверяют `revision`; конфликт блокирует повторное сохранение до загрузки актуальной версии. Сначала можно скачать свои несохранённые ответы. Облачное сохранение выполняется кнопкой; автоматическое локальное сохранение работает только для гостя.

Настроить Authentication → URL Configuration: разрешить `http://127.0.0.1:4173/profile.html` (подробности в корневом README). Затем создать аккаунт через сайт, подтвердить email, войти и сохранить анкету. Локальную ссылку нужно открыть на компьютере с запущенным сервером. При деплое добавить публичный адрес, настроить доставку писем и проверить весь цикл заново.

## Проверки доступа перед публикацией

- Анонимный клиент не читает и не меняет таблицу.
- Пользователь A читает, создаёт и меняет свой профиль.
- Пользователь B не читает, не меняет и не удаляет профиль A.
- Нельзя записать профиль с чужим `user_id` или изменить владельца.
- При обновлении `revision` увеличивается, а `created_at` сохраняется.
- Два обновления одной версии не должны молча затереть друг друга.

`verify.sql` проверяет настройки, но не заменяет проверки с токенами двух пользователей. Административный SQL Editor может обходить RLS.
